Chapter 01 · version fields

Version and compatibility model

7.7.0 is the exact package-compatibility base. Revision 1 produces the displayed release 7.7.0.1. Patch sets may apply only when their declared base, mode, host architecture, and target architecture match the selected installation.

        Chapter 03 · capability evaluation
        
    Capability requirements and detector mapping
    
        
    Each capability entry names one core requirement and a minimum runnable state. The CLI adds the three shared requirements, then evaluates compiled XML component aliases and executable checks for all four requirements.

    Compiled detector
    for the core requirement
    
            
    Routing Service is present only when metadata and the executable agree. These rules are compiled into V1.
    
            
    
          
    
        
    

        
    Evaluation
    Gateway requires Routing Service plus WAN, Security Plugins, and OpenSSL. Its minimum runnable base is 7.3.0. The selected channel is evaluated separately to determine whether 7.7.0.1 should be recommended.
    

        
    Separation of concerns: the capability entry determines whether the requested command may run now. The channel entry determines the recommended product state and patch set. For 7.7.0.x, both channels apply globally to Gateway, Spy, and Observability; the explicit capabilities arrays in the channel objects make that scope visible.

    Package sets
    LM uses the 11-file public patch set. Non-LM uses a nine-file private set derived from the 7.7.0.1 release package definitions. The .dmg is reserved for a machine with no usable installation.
    

        
    No usable installation? The matrix lookup collapses to one choice: download the public LM single bundle for the platform, verify it, print installation instructions, and ask the user to rerun. On latest, the overlay is offered only after the base installation is discovered.
    
      
    

      
    
        Chapter 06 · planner inputs and outputs
        
    CLI planning algorithm
    
        
    The planner evaluates capability, channel, installation metadata, host platform, and target architecture. It returns one of four outcomes: continue, install an ordered public patch set, display an ordered private package list, or download an LM installer.
    

        
    
          
    LoadVerify signature, schema, dates, revision.
    
          
    DiscoverRead candidate installations and metadata.
    
          
    ClassifyLM, non-LM, or unknown—not a boolean guess.
    
          
    ComposeCore requirement + three shared requirements.
    
          
    Read rowStable or latest names version and packages.
    
          
    MatchExact base + platform selects one explicit entry.
    
          
    ActContinue, install a package, list files, or download.
    
        
    

        
    
          
    Existing LM 7.7.0 · 11-package patch
    Patch the selected root in place.
    Match exact version, mode, host, and target; show every file; download and verify the whole set; then install in source order.
    
          
    New installation · LM bundle
    Download only. Stop safely.
    Verify the installer, show the authoritative instructions, do not execute it, and tell the user exactly how to resume.

    V1 implementation boundary
    
    Release metadata is external; installation mechanics remain compiled.
    
    
    Build & Release publishes versions, filenames, URLs, checksums, package sets, and channel policy. The CLI owns discovery, detector implementation, validation, confirmation, installation commands, and post-install verification.
    
    
    
      
    DeclarativeNo scripts in the manifest.
    
      
    ExplainableEvery action traces to a channel row and artifact role.
    
      
    Mode-safeLM and non-LM never silently mix.
